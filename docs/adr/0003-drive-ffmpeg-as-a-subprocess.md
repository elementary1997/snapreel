# ADR-0003: Захват и кодирование — внешним процессом ffmpeg

## Status

Accepted (2026-09-05)

## Context

Нужно снимать прямоугольник экрана на четырёх разных стеках (gdigrab,
x11grab, avfoundation, wlroots) и кодировать в H.264 с приемлемым размером
файла. Питон-библиотеки для этого либо тянут тяжёлые бинарные колёса (PyAV,
imageio-ffmpeg), либо не умеют захват (только кодирование), либо не покрывают
все три платформы (mss + ручная сборка кадров).

Отдельное требование: у проекта не должно быть рантайм-зависимостей на PyPI,
чтобы установка сводилась к «есть Python — работает».

## Decision

ffmpeg (и `ffprobe` для метаданных) вызывается как внешний процесс. Каждый
бэкенд — класс с чистой функцией `build_command()`, возвращающей список
аргументов. Запуск, останов и чтение stderr живут в общем `backends/base.py`.

Останов — запись символа `q` в stdin процесса. Для `wf-recorder`, который
такого не понимает, — SIGINT; это описано полем `graceful_stop`.

## Consequences

+ Нулевые рантайм-зависимости Python: `pip install snapreel` не тянет ничего.
+ Команды тестируются без запуска ffmpeg — сравнением списка аргументов.
+ Пользователь может подменить бинарь (`ffmpeg` в конфиге) или добавить свои
  флаги, не трогая код.
- ffmpeg надо ставить отдельно; это взял на себя `snapreel setup`.
- Ошибки приходят текстом в stderr, приходится их парсить и показывать хвост.
- Кадры не проходят через Python, то есть обработать их на лету (замазать
  область, наложить курсор иначе) без фильтров ffmpeg нельзя.

## Alternatives considered

- **PyAV** — умеет кодирование, но захват экрана всё равно требует устройства
  ввода ffmpeg; плюс тяжёлые колёса под каждую платформу.
- **imageio-ffmpeg** — по сути тот же внешний ffmpeg, но со своей копией
  бинаря (+70 МБ) и без контроля над аргументами захвата.
- **mss + покадровая сборка в Python** — работает на Windows/X11/macOS, но
  даёт нестабильный fps, нагружает CPU и всё равно нуждается в кодировщике.
- **OBS через websocket** — требует установленного OBS; несоразмерно задаче.
